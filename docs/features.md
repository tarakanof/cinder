# Firmware feature notes

Design, measurements and user decisions per feature, in build order. Hardware facts and toolchain: [`llm.md`](llm.md). How to build and flash: [`workflow.md`](workflow.md).

Issue numbers written as #N or cinder#N refer to the original private repository; Ember#N refers to the public [Ember](https://github.com/tarakanof/Ember) repository.

## Bot face (step 2) and rendering performance (measured 2026-10-03)

Step 2 done: `components/bot/` (pure C: `bot_behavior` = port of Ember's BotBehavior.swift, `bot_shape` = body ring + eye strokes, `bot_raster` = AA stroke rasteriser), host tests in `firmware/test/host/run.sh` (blink rates, eye swap behind blink, sleepy at 300 s, triangle geometry, rasteriser == per-pixel reference on 1500 cases). View: `main/bot_view.c`. Demo inputs: turn = look, push/touch = hop, long hold = next mood.

What made it smooth (refresh ms, before → after): 3-layer glow lines 250 → eyes-only 8-10; hop 250 → ~40; happy eyes draw 46 → 13.
- **Build `-O2`** (`CONFIG_COMPILER_OPTIMIZATION_PERF`); IDF's default `-Og` made loops ~2x slower.
- **Local BSP copy** `components/bsp_knob` (Apache-2.0): 2 draw buffers in internal DMA RAM (2×472×60×2 B) instead of 1 in PSRAM.
- **LVGL refresh 16 ms** (`CONFIG_LV_DEF_REFR_PERIOD`), frame timer 16 ms.
- **Own rasteriser**, not lv_line/borders: LVGL's wide AA round lines are very slow; a full-face circle-border object added 4-8 ms to every eye refresh. Eyes = RGB565A8 canvases (alpha so the outline shows through), span-based (exact capsule interval per row, distance only on the AA fringe).
- **Outline = one 448×448 opaque RGB565 image**, rendered on mood change only (~120 ms, behind the blink), moved as a whole for the hop. Dead ends: tiles (48 px or 16 px). Each small area is a separate QSPI transfer (160 tiles: 500 ms/frame), and LVGL falls back to full-screen redraw beyond 32 invalid areas (`LV_INV_BUF_SIZE`).
- **Never log from the LVGL task**: USB-Serial/JTAG console writes can stall without a reader; stats log runs in its own task.
- LVGL task stack is 8 KB (BSP default): keep big scratch arrays static (one overflow crash seen). `tri_build`'s 5.8 KB table scratch was the last such local until 0.9.32 ("Task stacks and internal RAM").
- `idf.py -DCMAKE_C_FLAGS=...` is cached in `build/toolchain/cflags` and silently persists; use source defines or `fullclean`.
- **Outline squash**: 11 pre-rendered variants (5 squash, base, 5 stretch, ~4.8 MB PSRAM) drawn by a core-1 task after each mood change (~1.3 s); the LVGL task is pinned to core 0 (BSP copy). Hop frames ~40-60 ms. LVGL image scale transform was ~160 ms/frame. Redrawing only the ring as 20 slices or 4 bands was no faster (~3 ms fixed cost per area) and **broke the ring at the seams** (areas reach the panel at different times), so the outline is invalidated as one area.
- **Hop tuned for the knob** (user): 1.0 s instead of 0.62 s, squash × 0.75 (`BOT_HOP_DURATION_S`, `BOT_HOP_SQUASH`).
- **No tear sync possible (re-checked 2026-10-05, #42)**: with TEON now sent with its parameter byte (the init table sent 0 bytes; RDDSM 0x0E reads 0x80 = TE on), no free GPIO (7, 15, 16, 18, 21, 38-42, 45-48) toggles: all follow their pull-up/pull-down, so TE is not routed to the ESP. Panel reads work over a 3-wire half-duplex SPI device on SIO0 (GPIO13) with CS (GPIO12) driven by hand at 5 MHz (0x0A → 0x9C, 0x0C → 0x55, 0xDA → 0x53, 0x52 → brightness), but GSL 0x45 always reads 0, so no scanline either. Earlier note: the schematic's "TE" on GPIO38 floats on this unit (TE waits always time out, idle level random across boots), and the adapter's TE mode needs a 440 KB full-frame buffer that only PSRAM can hold, which QSPI DMA can't send (ESP_ERR_NO_MEM). Some tearing during the hop remains; smaller per-frame motion reduces it.
- Free memory at runtime (bot face): internal ~125 KB (largest block 54 KB), PSRAM ~3 MB before the 11 variants. Wi-Fi will need internal RAM: don't grow the DMA draw buffers.
- Eye raster history: per-pixel distance cost up to 46 ms per frame for the happy eyes; the span raster solves each segment's capsule x-interval per row (outer radius = any coverage, inner = full) and computes distance only on the 1-2 px fringe. libm `atan2f` dominated the glint raster on the S3 (hence the polynomial, max error ~0.06 deg).

## Ember over Wi-Fi (step 3, done 2026-10-03)

`main/ember_client.c`: Wi-Fi STA + poll `GET /state` every 2 s on core 1; mood = Ember's render priority on `render.{waiting,errors,running,done}`. Long hold = demo mood for 20 s, then Ember again. Credentials + URL in NVS since #6; the git-ignored `firmware/sdkconfig.secrets` is only the opt-in dev seed since 0.9.16 (see "Secret-free builds"). Ember on the LAN, e.g. `http://ember.local:3627` (from `~/.config/ember/producer.env`).
Internal RAM budget (the hard constraint): Wi-Fi must start **before** the display; `CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM=8`, `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y`, `CONFIG_LV_USE_CLIB_MALLOC=y` (LVGL's fixed 64 KB internal pool freed). Result: ~64 KB internal free, rendering unchanged (avg ~8.5 ms, max ~23 ms). Tearing tracked in GitHub issue #1. Weather animation: procedural sprites in one sky canvas.
- Starting Wi-Fi after the display failed with `16 rx buffer, actual is 13` (static RX buffers need internal DMA RAM before the draw buffers take it). HTTP timeout 5 s: a lost SYN or segment costs a 1.5 s RTO plus the retry; 3 s was too short.

## Pages: bot, Pomodoro, weather (step 4, PR #4, verified on hardware 2026-10-03)

`main.c` owns a page index; push and turn (button held while turning) changes page, and that press does nothing else. Push vs long push is decided on **release** (a hold followed by a turn is a page change, so long push must not fire at 1.5 s). Inputs are counted as atomics in the esp_timer input callbacks and applied in the LVGL `frame_cb`, which knows the page. The callbacks keep the atomics; what a turn or a release means (dropped by the reset gesture, page step, detent; push, long push, nothing) is `cinder_cfg/press_route.c`, host-tested in `test_legacy.c`. Hidden pages don't draw; the bot keeps its timers off-page and redraws its full pose on return.
- Pomodoro (`components/pomo`, `pomo_client`, `pomo_view`): poll `/v1/pomodoro/state` 1 s running / 2 s idle, actions POST with bearer from a core-1 queue (action chosen from the freshest state, like Ember's `pomoMiddlePress`). Bezel arc = one 472×466 PSRAM canvas, per-second dirty rect ≤24×24 px. Offline only after 3 failed polls (each online/offline flip is a full redraw); since 0.9.40 the shared link state plus the Pomodoro data's own freshness, and offline the page keeps counting (Offline fallback, below). Token: NVS (`dev_tok`, see issue #6 section); dev builds still compile the seed in.
- Weather (`components/weather`, `weather_client`, `weather_view`): poll `/v1/weather/state` every 10 min; 200×140 sky canvas, A8 sprite masks (~80 KB PSRAM), 4-12 fps by condition; day/night from Ember's sun times, no device clock.
- Free internal RAM with all pages: ~47 KB (largest 31 KB). Bot page: avg ~10 ms, max ~55 ms (the max is a hop frame, same as before).
- Panel dirty areas are rounded to 2 px: view code keeps offsets and heights even. Pomodoro ring: stroke centre r 222, 12 px wide, outer edge 228.5 just inside the glass; a colour change redraws every touching tile (~10-20 ms), a second tick redraws <= ~24x24 px at the arc end. Weather client: new connection per poll (10 min interval outlasts Ember's 120 s keep-alive); "hourly" arrays are emptied before cJSON parsing (~150 small allocations from tight internal RAM; `wx_legacy_drop_hourly`, which tracks bracket depth and skips strings, so a nested array or a `]` inside a string no longer cuts the body at the first `]`); response ~3.5 KB, 16 KB buffer in PSRAM.

## Host label and dimming (issues #2, #3, 2026-10-03)

- **Host label** (curved since #42, see below): `components/ember_host` (pure C, host-tested): `render.source` (Ember#213) when present, even `""`; older servers: port of Ember's `render.PickWinning` on `sessions[]` (waiting > error > running > done, strictly newer `updated_at` wins, parsed as RFC 3339 with offset, not compared as text; idle never wins), then "" unless every session in the winning state has the same source (as Ember#213). Uppercase, max 10 chars. One Montserrat 24 label at 0.8 r below the body centre, mood colour, visible in waiting/error only; text set only on change; it moves with the hop inside the outline's invalidated area (no extra area).
- **Dimming**: `components/dim` (pure C, host-tested) + the Ember poll task (core 1, no new task): `GET /v1/display/brightness` (Ember#212) every 60 s, then the 2 s wait between `/state` polls steps a fade (20 steps × 100 ms, floor 10). Non-200 (old server: 404/401) keeps the level; the startup level comes from the knob settings (default 153, also via the raw setter). Written as raw 0-255 WRDISBV with the driver's QSPI encoding (`0x02<<24 | 0x51<<8`), because the driver's percent API loses resolution and logs every call; since 0.9.35 the LVGL task writes it from a request (`panel_check_brightness`, newest level wins; architecture follow-ups below).

## Settings in NVS, setup face, factory reset (issue #6, 2026-10-04)

- Settings live in NVS namespace `cinder` (`main/config_store.c`, thin ESP layer; model + validation in `components/cinder_cfg`, host-tested): `wifi_ssid`, `wifi_pass`, `ember_url`, `dev_id`, `dev_tok`, `name`, plus `settings` (JSON blob ≤1 KB) and `settings_ver` reserved for #8. Loaded once at boot; copies live in PSRAM. Secrets never logged (`cfg_describe`).
- **Dev seed** (opt-in since 0.9.16): the Kconfig values (`sdkconfig.secrets`) are written to NVS once, on a boot where the namespace has no keys and the SSID is set (log `config: NVS empty: seeded from the build config`). Wi-Fi and the Ember URL only; the token seed is gone (0.9.16).
- No SSID → **setup face** ("Connect to a Mac with Ember" + `ID XXXXXX` (last 3 bytes of the base MAC)); Wi-Fi is not joined (since #7 the radio starts for Improv scans only). No Ember URL → Wi-Fi only, no pollers.
- **Factory reset**: hold 10 s without turning → overlay; keep holding and turn right 24 detents (one turn). Release, a left detent or 5 s without a right detent cancels; that press is then not a push / long push / page change. Confirm → erase `cinder` + `esp_wifi_restore()` + reboot (from a core-1 task, not the LVGL task). Not tested on hardware (it wipes the user's Wi-Fi; Improv USB provisioning restores it).
- **Internal RAM is at the edge before the display**: +1.8 KB of new `.bss` made the second 56 KB LVGL draw buffer fail (`alloc secondary buffer 56640 bytes failed`, boot loop). Keep new buffers in PSRAM or on existing task stacks; `main` logs free/largest internal before the display init.
- **Dev seed is gated** by `CONFIG_CINDER_DEV_SEED` (default n; only an opt-in `-D CINDER_SEED_SECRETS=1` build layers `sdkconfig.secrets`, which sets y; the SSID/password/URL Kconfig options `depends on` it, so they are not compiled in otherwise). Seeds when the namespace is empty or has keys but no SSID (`wifi_ssid` is saved last, so a cut-short save reseeds); never on an NVS lookup error or over a provisioned config (`cfg_should_seed`, host-tested). A bad SSID/password in the build config → no seed (setup face); a bad URL → left empty. The log names the key, never the value.
- SSID (32 B) and PSK (64 hex) are copied into `wifi_config_t` without a NUL (`cfg_copy_raw`), as the driver expects.
- Wi-Fi keeps the driver's default flash storage (as before #6). The first association after boot often fails (reason 203) and the IP comes ~5 s later; seen with both RAM and flash storage, not caused by it.

## USB provisioning: Improv Serial + CINDER1 (issue #7, 2026-10-04)

- `components/provision` (pure C, host-tested): Improv codec + RX demuxer (`improv.c`), CINDER1 request parser and reply writer (`cinder_line.c`, cJSON). Shared vectors in `firmware/test/vectors/{improv,cinder1}.json`; they also pass against Ember's `ImprovCodec.swift` / `CinderLineCodec.swift` (checked 2026-10-04). Host tests compile cJSON from `$IDF_PATH` (source the ESP-IDF export script first).
- `main/provision_usb.c`: `usb_serial_jtag_driver_install` (512 B RX + 512 B TX rings) + `usb_serial_jtag_vfs_use_driver`, listener task core 1 prio 2, 3.5 KB stack (3 KB left only ~700 B headroom; 5 KB since 0.9.32), buffers in PSRAM. Started after the display init. Every frame/line is written in one piece under `flockfile(stdout)`: ESP_LOG writes stdout under the same lock, so logs never split a frame. Nothing is written when no USB host is on the cable (`usb_serial_jtag_is_connected` is SOF-based: it does not know whether the port is open); with the Mac attached and the port closed, each 256 B chunk waits at most 50 ms while holding the stdout lock.
- While the host talks, logs drop to WARN (back to the default level 30 s after the last message, with the listener's stack headroom in the log).
- **Opening the port does not reset the knob** when the host leaves DTR/RTS alone (raw termios, `HUPCL` cleared; no pyserial). `esp_restart()` keeps the USB-Serial/JTAG port: the same open fd reads the next boot (verified), so Improv's "provisioned" result arrives on the host's session after the reboot.
- Improv: 0x01 Wi-Fi → validate, save to NVS, state `provisioning`, reboot (Wi-Fi must start before the display); an RTC_NOINIT flag makes the next boot send state `provisioned` + result `http://<ip>/` after GOT_IP, or error 0x03 after 3 credential-type disconnects (`improv_join_failure_reason`: 2, 15, 201, 202, 204, 210, 211; not 203, which the first association at boot often gives; since #21 counted since the last IP; 2/15/204 below −80 dBm count half (`improv_join_note`, 8 weak handshake timeouts → reported), other reasons neither count nor reset). The screen shows "Can't join <SSID>" (top layer) while that lasts. 0x02 state (+ URL when online), 0x03 info `["cinder", fw, "ESP32-S3", name or "Knob XXXXXX"]`, 0x04 scan (≤20 results, then an empty one), 0x06 device name; others → error 0x02.
- CINDER1: `info`, `set_ember`, `status`, `reset {factory|ember|wifi}`, `reboot`; events `boot`, `ember` (ok/unreachable/unauthorized), `wifi` (`invalid`). Replies use sorted keys; secrets are never echoed. Contract with the app (2026-10-04): Ember URL is **http only** (no TLS on the knob: no CA bundle, esp-tls would refuse), scheme case-insensitive and lowercased with the host, host IPv4 or `[a-z0-9.-]` (no IPv6 literal, `_`, IDN), port optional, no path, ≤128 chars (`cfg_url_valid` / `cfg_url_normalize`); device_id `[A-Za-z0-9_-]` ≤32; token ≤64 printable; name ≤32 **bytes** UTF-8, empty or absent keeps the stored name. `set_ember` saves; the token applies to the next request; a changed (or first) URL on a knob with Wi-Fi reboots it right after the reply so the pollers start with it (without Wi-Fi the Improv Wi-Fi RPC reboots anyway). An Improv Wi-Fi RPC whose SSID/password fails the knob's checks (PSK 8-63 printable ASCII or 64 hex, SSID 1-32 bytes) gets Improv error 0x01 (spec) plus `{"ev":"wifi","state":"invalid"}`. With `CINDER_DEV_SEED`, `reset wifi|factory` reseeds Wi-Fi from the build config on the next boot.
- Setup face: the Wi-Fi radio starts (before the display) for Improv scans only, with `WIFI_STORAGE_RAM`; it never joins. Free internal 67-74 KB there (forced-setup test build, NVS untouched).
- One request at a time: the RX ring holds 512 B and a burst of 40 requests lost most of them (no flow control on USB-Serial/JTAG RX). A frame cut short by lost bytes is dropped after 100 ms of silence (`prov_rx_idle`).
- **Internal RAM**: the driver pulls in `esp_ringbuf`, whose code defaults to IRAM (~4 KB of DIRAM). `sdkconfig.defaults` now sets `CONFIG_RINGBUF_PLACE_FUNCTIONS_INTO_FLASH=y` + `..._ISR_FUNCTIONS_INTO_FLASH=y` (the USJ ISR is not IRAM). An existing `sdkconfig` keeps the old values: set both or regenerate it. Measured with all pages: free internal 46 KB (largest 31 KB) at runtime, 40 KB right after boot; render avg 9-10 ms (unchanged).
- Test client: raw termios + Improv/CINDER1 demux in ~150 lines of Python (no pyserial needed).

## Device token, checkin, settings from Ember (issue #8, 2026-10-04)

- Pure C in `components/provision`: `knob_settings.c` (Ember's knob settings v1 → `knob_settings_t`, defaults + clamps: floor ≤ level, startup ≥ floor, poll 1-10 s; unknown page ids kept but not shown; no page on → all pages) and `device_api.c` (checkin body with sorted keys, answer parse, schedule: at boot, every 60 s, on a changed `X-Ember-Devices-Epoch` no sooner than 2 s after the last checkin, failure backoff 60 s → 5 min). Host tests `test/host/test_device.c`.
- **Unpaired until a device token** (0.9.16; before it a token without `dev_id` was the legacy `EMBER_TOKEN` and Pomodoro used it): the knob never checks in and makes no authenticated call; it reads the unauthenticated legacy endpoints and shows "Not paired". `set_ember` over USB stores `dev_id` + device token; the next request uses it and a checkin follows at once (token generation counter), no reboot needed unless the URL changed.
- Checkin runs on the existing `ember` poll task (core 1): `POST /v1/devices/self/checkin` with `fw`, `ip`, `rssi`, `heap_internal_*`, `uptime_s`, applied `config_version`. The epoch header is read from the `/state` GET with an `esp_http_client` event handler (`get_header` only reads request headers). Measured on hardware: settings PUT → applied in 1.75-1.9 s (poll 2 s); ember task stack headroom 3.8 KB.
- `new_token` → `config_store_set_token` (NVS commit first, then the RAM copy the next request reads) → immediate checkin, which promotes it on the server. USB `status`/`ember` events with a device id: `connecting` until a checkin returns 200 since boot or the last token change over USB (a server-issued rotation does not reset it), then `ok`; legacy mode keeps the `/state`-only meaning (`dev_link_combine`, host-tested). 401 → state `unauthorized`: "Not paired" label (top layer), Pomodoro note `NOT PAIRED`, Pomodoro writes stop; `/state`, weather and Pomodoro reads keep working. A new token over USB clears it.
- Settings live: brightness (follow Ember or fixed level, floor via `dim_fade_set_floor`, startup level at boot), page list + home (LVGL task picks them up by a generation counter; the current page stays unless it was turned off, then home), `poll_ms` (Ember + Pomodoro idle), `bot.sleepy_after_s` (`bot_set_sleep_after`, 0 = never), `bot.demo_hold_s`. Stored as the JSON blob `settings` + `settings_ver` in NVS, loaded at boot. `CINDER_EMBER_POLL_MS` is only the default before the first settings.
- **RAM**: the first version kept ~1.1 KB of new state in `.bss` and the display's second 56 KB draw buffer failed again (boot loop, `alloc secondary buffer 56640 bytes failed`). All new poll-task and LVGL-task state is now in PSRAM; `.bss` is below #7's. Runtime with checkins: internal free ~45.3 KB (largest 30.7 KB), flat over 4 min.
- Verified against a scratch Ember (main @ dc0c63f, port 3628, temp DB, mDNS and clock discovery off): mint → `set_ember` → reboot → checkin + settings v1; PUT ×4; rotate (new token stored, promoted, `rotation_pending:false`); DELETE → 401 → unauthorized; re-mint + `set_ember` → ok without reboot; pages off → home page. The live server (v0.34.0) has no `/v1/devices` yet; the knob was put back on its legacy config afterwards (one-off forced dev-seed build).

## Performance quick wins (2026-10-04)

Measured on the knob (paired, bot page, mood working, RSSI −68 to −73 dBm): flash, reboot over USB (CINDER1 `reboot`, same fd), 10 min passive serial capture, CINDER1 `status` at 5 and 10 min. Boot-to-mood = log time of the first `Ember mood -> N` (N ≥ 0); it varies ±2 s with Wi-Fi association.

|---|---|---|---|---|---|---|
| main (dc84b8e) | 40 / 31 KB | 45.2 / 31.7 KB | 9.3 / 36.8 ms | 0 (0 IDF error lines) | 1.9 → 3.8 s | 1,561,824 B |
| #18 HTTP reuse | 40 / 31 KB | 40.2 / 31.7 KB | 8.9 / 26.8 ms | 0 of 545 requests, 3 TCP connects | 3.1 → 6.0 s | 1,563,760 B |

- **#18 HTTP reuse** (`main/http_conn.c`, `components/net_policy/fail_streak.c`): one esp_http_client handle and socket per poller (ember: `/state`, brightness, checkin; pomo: state + actions); weather stays one connection per request (10 min > Ember's 120 s idle timeout). 545 requests in 10 min used 3 TCP connections (before: one per request). Timeout 5 s; a failure on a reused socket is retried once on a new one (Pomodoro actions are not idempotent: retried only when the socket failed to open or closed before any status line, `components/net_policy/http_retry.c`); the whole body is read; Wi-Fi loss bumps a generation counter and the owner closes its stale socket (no cross-task close). Network errors are transient until 3 in a row (mood, host label, USB link state keep their value) and are logged once per streak + every 60 s + on recovery; `esp-tls`, `transport_base`, `transport`, `HTTP_CLIENT` are set to NONE (re-applied after the USB session's `esp_log_level_set("*")`, which clears per-tag levels). The stats task logs `net: N req, F failed, R retried, C new connections | internal free`. Cost: the two kept handles hold ~5 KB of internal RAM (`SPIRAM_MALLOC_ALWAYSINTERNAL=16384` puts their small allocations there); the largest block is unchanged. Pomodoro actions retry only before any status line: a timeout, failed body write or cut response may mean the server applied the action (RFC 9110 9.2.2), and a second skip skips two phases.
- **#21 Wi-Fi reconnect** (`ember_client.c`, `components/net_policy/wifi_backoff.c`): the disconnect handler no longer sleeps 2 s in the default event loop (that held IP events behind it). It arms a one-shot esp_timer: 1, 2, 4, 8, 16, 30 s, reset on GOT_IP; the timer callback calls `esp_wifi_connect()` only while provisioned, and re-arms with the next step when the driver refuses to start a connect (no disconnect event would follow). The rest of #21 (HT20, scan, jitter, telemetry) is in its own section below.
- **#20 build config** (`sdkconfig.defaults`, `CMakeLists.txt`): static D/IRAM 156.4 → 94.7 KB (`.bss` 43.7 → 10.3 KB, IRAM `.text` 90.9 → 62.5 KB); flash use −58 KB (LVGL −89 KB); boot to UI 2.39 → 2.17 s (bootloader loads the app in 273 ms instead of 333 ms).
  - **Flash QIO 80 MHz** works on this unit: bootloader logs `qio_mode: Enabling default flash chip QIO` / `SPI Mode : QIO`, app `flash io: qio`. Puya 0x85/0x2018 has no entry in IDF's QE table; the default entry (RDSR2 0x35 / WRSR2 0x31, QE = SR2 bit 1) sets it. The schematic wires flash WP/HOLD to SPIWP/SPIHD through 0R (R17/R18); VIEWE's own encoder15 PlatformIO board uses QIO. The stock firmware was DIO. If QE could not be set, the bootloader would stay in DIO (it does not fail). `idf.py flash` shows `--flash_mode dio`: normal for QIO (the ROM loads the bootloader in DIO).
  - `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY=y` moves `EXT_RAM_BSS_ATTR` arrays (the 2 outline `rim_work_t`, 13.3 KB; `bot_shape.c` `s_tri`, 5.8 KB) **and, by IDF's own linker rules, the `.bss` of net80211, lwip, pp and wpa_supplicant** (~14 KB) to PSRAM. Wi-Fi IRAM/RX-IRAM opts off (pp −14 KB IRAM) and FreeRTOS in flash (−10 KB IRAM).
  - D-cache 64 B lines; LVGL SW renderer without RGB565_SWAPPED, RGB888, XRGB8888, ARGB8888_PREMULTIPLIED, L8, AL88, I1 (ARGB8888 kept: LVGL's alpha layers use it); `LV_INV_BUF_SIZE=64` for every component (it sizes a struct in `lv_display_private.h` that the adapter also includes).
  - Largest free internal block stays ~31 KB: that is the region layout, not fragmentation. The block before the display grew 124 → 184 KB (DMA).
- **#22 boot brightness + core dump**: the CO5300 init table sends 0x51 = 0x00 and the BSP copy no longer calls `set_brightness(100)`; the panel stays dark until `main` sets the startup level after the UI is built (no full-brightness flash). Core dump to flash (ELF, CRC32, `FLASH_NO_OVERWRITE`: the first dump is kept) in a new 64 KB `coredump` partition at 0x820000, carved from the start of the unused `storage` (now 0x830000, 0x7D0000). nvs/otadata/phy/OTA offsets are unchanged, so `idf.py flash` (which also writes the new table) keeps NVS: the knob stayed paired (checkin ok, config v5). Boot logs `reset reason N` and, if a dump exists, `core dump in flash: task …, pc …`; read it with `idf.py coredump-info`, clear with `idf.py coredump-erase`. A partition that is neither blank nor a valid dump (old storage bytes, a dump cut short) is erased at boot, because `FLASH_NO_OVERWRITE` would otherwise block every later dump. Cost: ~4 KB internal (the panic handler's 1.8 KB core dump stack in `.bss`, `ESP_COREDUMP_USE_STACK_SIZE` because task stacks may be in PSRAM) and 16 KB flash. The rest of #22 (checkin `diag`, task WDT, bootloader): see "Field diagnostics in every checkin".

## One poller on Ember's knob view (#24, 2026-10-04)

- With a device token the ember task reads `GET /v1/devices/self/view` (Ember#234) instead of `/state`, `/v1/pomodoro/state`, `/v1/weather/state` and `/v1/display/brightness`: bearer on the GET, `If-None-Match` with the last good view's ETag, 304 = unchanged (empty body, never parsed; the cached view is handed to the pages again with the new `X-Ember-Now`). ## Field diagnostics in every checkin (#22, 0.9.13)

- Every checkin carries `diag`, whatever `config.diagnostics` says (`stats` stays opt-in and unchanged). Keys sorted; Ember ignores unknown checkin fields until it stores them:
  `"diag":{"boots":42,"crash":{"pc":"0x4201a2b3","reason":"panic","task":"ember"},"heap_internal_min":71234,"heap_largest_min":30720,"reset_reason":"poweron","stack_free":{"ember":1880,"eye":900,"link":1500,"lvgl":2304,"pomo":2100,"prov":1400,"rim":3000,"stats":1100,"weather":2900}}`
  - `boots`: NVS counter (namespace `diag`, key `boots`), one write per boot. `reset_reason`: `esp_reset_reason()` name (same names as `stats.reset_reason`).
  - `heap_internal_min`: `heap_caps_get_minimum_free_size(INTERNAL)` since boot. `heap_largest_min`: lowest largest internal free block seen; IDF keeps no such minimum, so `diag_track` samples it at boot, every 30 s (stats task) and at each checkin.
  - `stack_free`: bytes never used (`uxTaskGetStackHighWaterMark`) for our long-lived tasks that exist (setup face: no `eye`, `rim`). Tasks missing at the time are left out. `orbit` is not reported: it deletes itself a few seconds after boot, before the first checkin.
  - `crash` only while a valid dump is in the `coredump` partition, so every checkin repeats it until the dump is erased (since 0.9.14 after Ember stores it, see the core dump upload section below; or `idf.py coredump-erase`). `task`/`pc` come from `esp_core_dump_get_summary`, except for `task_wdt`: the TWDT panics whatever runs on a core at that moment, so the dump's task is not the culprit. For that case `esp_task_wdt_isr_user_handler` copies the first entry that missed its reset (`esp_task_wdt_print_triggered_tasks`, e.g. `ember` or `IDLE1`) into `RTC_NOINIT` memory; the next boot stores it with the dump (`dump_wdt`) and reports it as `task` (`twdt` if nothing was recorded). For `task_wdt`, `pc` is where the panicking core was interrupted, not where the culprit hung. The dump has no reset reason, so the boot that first sees a dump stores its CRC32 and that boot's reset reason in NVS (`dump_crc`, `dump_rr`); `reason` is `panic`, `int_wdt`, `task_wdt` or `wdt`, else `unknown` (a dump left from an older firmware). A task name that is not printable ASCII is dropped.
- Checkin body buffer 768 → 1280 B (PSRAM); worst case with stats and wifi is ~1 KB.
- **Ember task watchdog.** The task WDT keeps 5 s for the idle tasks and now panics (`ESP_TASK_WDT_PANIC`: core dump, reset reason `task_wdt`). The ember task cannot feed a 5 s WDT itself: one request may block ~20 s (5 s connect + 5 s read, one retry) and a view long-poll for its whole wait. So it is a TWDT *user* named `ember`, fed by a 1 s `esp_timer` while the task stamped itself in the last 90 s (loop top, every wait slice, every long-poll idle slice, after the view poll and the checkin, and at the start of every request on the ember connection through `http_conn_t.on_request`), so the budget covers a single request, not a chain. A poller stuck for 90 s stops the feeding and the TWDT panics within 5 s. If arming fails half-way the user is deleted again, so nothing unfed stays subscribed. Risk: an idle task starved for 5 s now resets instead of only logging. Long CPU-bound work on core 1 therefore yields: the boot `orbit` fill computes 8 entries (~24 ms at ~3 ms per solve) then `vTaskDelay(1)`, so IDLE1 runs at least every ~25 ms; 180 extra ticks add ~0.2 s (~4 %) to the ~4.3 s fill (estimate, not measured on the knob). The `rim` task yields 1 tick after each outline variant (~0.12 s each, +11 ms per mood change). Checked and left alone: the glint mask (one 45th of the ring per frame, lazily, in the LVGL task), the `eye` task (one eye per frame, blocks on a semaphore) and LVGL glyph caching all return within a frame, and the LVGL task sleeps between frames, so IDLE0 runs every frame (~2 % at a 60 fps chase).

## Core dump upload and erase after ack (#56, Ember#311, 0.9.14)

- `diag.crash` gains `id` and `size`: `"crash":{"id":"1a2b3c4d","pc":"0x4201a2b3","reason":"panic","size":20516,"task":"prof"}`. `id` is the CRC-32 that IDF stores in the last 4 bytes of the flash image (LE, 8 lower-case hex): zlib CRC-32 of the image without those 4 bytes. `size` is the whole image (`esp_core_dump_image_get`), which is also the upload body.
- **Why not the CRC of the whole body** (the first draft of the contract): the image ends with its own CRC-32, and CRC-32 of data followed by its own CRC (LE) is always `0x2144df1c`. Every dump would get the same id, and Ember's "already stored" check would ack a new dump without an upload. User decision 2026-10-06: option A, Ember verifies `crc32(body[:-4]) == id` and `body[-4:] == id`.
- No extra pass at boot: `esp_core_dump_image_check` (already in `diag_boot`) streams the partition and validates that stored CRC, so the id is read, not computed.
- Checkin reply (both optional, 8 lower-case hex, anything else ignored): `coredump_wanted` equal to the current id arms an upload; `coredump_ack` equal to the current id erases. A reply without `coredump_wanted`, or for another id, disarms it. An old server sends neither, so nothing changes.
- **Upload** on the ember task, right after the checkin that asked, never while a Pomodoro phase is running (`pomo_mode == RUNNING`; paused, parked and idle are fine): `PUT /v1/devices/self/coredump?id=<id>`, device token, `application/octet-stream`, `Content-Length` = size, on the ember keep-alive connection (`http_conn_req_opts` with a `read` callback). The body is copied in 4 KB chunks from a flash mapping (`esp_partition_mmap`) into a 4 KB PSRAM buffer, then written; `alive()` per chunk. `esp_partition_read` into a PSRAM buffer is not used: IDF bounces such reads through an internal `malloc` of the read size (`spi_flash_os_func_app.c`, `get_buffer_malloc`).
- **Self-check**: the CRC-32 is streamed over the chunks; if it or the trailing 4 bytes do not equal the id when the last chunk is read, the request is aborted before that chunk is sent (Ember sees a short body), and it counts as a failed upload.
- **Backoff** after every upload attempt (failed, or 2xx but still wanted at the next checkin): 1 min, 5 min, then 30 min. The dump stays and `crash` keeps being reported. A 204 triggers a checkin at once to collect the ack.
- **Erase** only after a matching `coredump_ack`, on the ember task's next loop pass, and never while a Pomodoro phase is running (same guard as the upload; the ack sticks until then). `esp_core_dump_image_erase` erases the 64 KB partition: it is 64 KB-aligned and `CONFIG_SPI_FLASH_BYPASS_BLOCK_ERASE` is off, so that is one 64 KB block erase, typically 0.15-2 s with the flash cache off, and the display can stall once for that long. Then the NVS `diag` keys `dump_crc`, `dump_rr` and `dump_wdt` are removed, the in-RAM crash is cleared, and a checkin follows at once so Ember sees `crash` gone. If the erase fails, the dump and the record stay, and the erase is retried after 1, 5, then 30 min (one error log per streak), so a failing block is not erased once per checkin.
- Cost (static): image +3.2 KB (1,636,023 → 1,639,235 B), internal `.bss` +16 B, DIRAM otherwise unchanged; poll context in PSRAM +~200 B. During an upload: 4 KB PSRAM and one 64 KB flash MMU mapping, both released after. Runtime not measured yet (needs a flash; the knob holds a real dump, task `prof`, as the first test).

## View long-poll (#27, Ember#235, 2026-10-05)

- Ember with #235 advertises `X-Ember-View-Wait: 25` on every view answer and holds `GET /v1/devices/self/view?wait=N` + `If-None-Match` until the view changes (200) or N s pass (304, same ETag). The knob sends `wait` only after it has seen the header (`P->wait_cap`, re-read on every answer: a downgraded server turns it off): an older server ignores the parameter and would answer at once. Without the header it polls every `poll_ms` exactly as before (verified on the live v0.37.0: `fw` 0.8.0 checks in, 30.6 req/min, 4.1 KB/min in, 6.2 KB/min out, render avg 6.6 ms, internal free 105.8 KB; 0.7.0 before it: 30.7 req/min, 4.5 / 6.2 KB/min, 6.6 ms, 105.4 KB).
- Pure, host-tested (`net_policy/view_wait.c`, `http_retry.c`, `test_net.c`): the header parse; `view_wait_s` = min(server cap, 25 s, whole seconds to the next checkin), 0 = plain poll below 2 s, without a cached view, or after a failed view request until a 200/304 (so a dead server is still found in ~3 plain polls, `OFFLINE_AFTER_FAILS`); HTTP read budget = wait + 10 s; re-arm at once after a 304 that took ≥ 1 s, 200 ms after a 200 (a view that changed on every read cannot spin the knob), else (error, 429, a 304 that did not wait) `poll_ms`; a long-poll is retried only when the reused socket was found closed (open/send/closed before a status line), never after a timeout (`http_should_retry_wait`).
- `http_conn` long-poll (`read_budget_ms`, `wake_fd`, `idle`): after the request is sent the ember task blocks in `select()` on the socket and an eventfd (`ember_client_wake`, written by `pomo_client_action`), then reads the head as a normal fetch. Between empty slices `longpoll_idle` steps the brightness fade (slice 100 ms while a fade runs, else 1 s: no 10 Hz wakeups) and gives the request up (`HTTP_CONN_ABORTED`: socket closed, so Ember frees the waiter; not a failure, no streak, mood and link unchanged) for a Pomodoro push (at once through the eventfd; run on the same handle, then the view again), a USB settings change, a new token or lost Wi-Fi (within 1 s). A push already queued runs before a wait is armed. Long-polls count in diagnostics (a success with its read time from the head, not the server's wait; a failure with its full time) and in tx bytes, aborted ones included.
- 429 (Ember's 2-waiter cap, e.g. quick pushes) backs off `poll_ms` and keeps mood and link, like a network error.
- Checkins keep their cadence (60 s, live mode): the wait never runs past the next one, and an epoch change ends in a plain poll + checkin. Ember's clock estimate takes `X-Ember-Now` from checkins, plain polls and waited answers that came back within 1 s; a longer waited answer bounds it only to the whole wait (and could restart the estimate from a 26 s interval after a server clock step), so it is left out.
- Offline detection: a server that closes or resets the socket fails at once; a host that vanishes mid-wait is found when the read budget ends (≤ 35 s), then two plain polls (~7 s each) → offline in ≤ ~50 s worst case (before: ~21 s). Host-tested logic only; not provoked on the knob (that needs a Wi-Fi or server change).
- No 1 s polls near a phase end while long-polling: Ember's phase change wakes the request.
- Not measured yet (needs Ember with #235 on the live server; scratch servers are off-limits for the paired knob): mood latency, req/min and KB/min with long-poll. Run `firmware/tools/measure_view_latency.py` after the deploy (it times POST/DELETE of a probe session → the knob's `Ember mood` line over USB and reads the HTTP counters; no change on the knob). Expected from the spec: latency < 100 ms + one DTIM (≤ ~300 ms) instead of avg ~1.15 s / max 2.8 s (#24), ~2-3 req/min idle instead of ~30.
- Firmware version 0.8.0 (0.9.0 since #14).

## Now-playing controls (Ember#280, firmware 0.9.6, 2026-10-05)

- Mapping (the page only; push and turn still changes the page): **turn** = volume (2 points per detent), **push** = play/pause, **double push** = next track, **long push** (decided on release, as everywhere) = previous track, **touch** = wakes the dimmed face only, on press (on every other page a tap is still a push; here a brush must not pause the music; since 0.9.15 a tap's push is decided on release, see "Vertical swipe between pages"). In a frame, detents are applied before pushes.
- Pure, host-tested `components/nowplaying/np_ctl.c` (`test_np.c` `test_ctl`): a push waits `NP_DOUBLE_S` 0.35 s (release to release) for a second one (then next, else play or pause); play/pause go out as the state wanted (`play` / `pause`, not a toggle), so two quick pushes can't both pause; volume detents add up and go out at most every 0.25 s (4/s; host test: 20 s of turning ≤ 81 commands); the full step is sent even at 0/100 (the shown level may be stale, the player clamps); nothing is sent while nothing plays (Ember would answer 409).

Badge priority: the level while turning, then the command's icon (0.8 s), then why a command failed (2.5 s: `Update Ember` for 401/404, i.e. an Ember without the route answering its owner-token catch-all; `No control` 503; `Nothing playing` 409, also when the shown track changed at Ember; `Slow down` 429; `Ember offline`). ### Core use and two-core work (0.9.10-0.9.11, on the cinder#51 prototype)

Question: can LVGL's parallel software draw units cut core 0 during a 60 fps chase (core 0 97-98 %, ~50 fps, core 1 ~1 %)? Answer: no. The chase load is mostly app code in the LVGL task, not drawing. What helped: the eye raster split across both cores, a gaze table instead of a per-frame solver, and the esp_timer and Wi-Fi tasks moved to core 1.

**Where core 0 went** (temporary per-task run-time profile, 5 s windows, chase at 60 fps, 0.9.9): LVGL task 89 % of core 0, of which `frame_cb` 54 % (`bot_orbit_gaze`, a 30-step double-precision bisection per frame: 18 %; `bot_view_update`: 33 %, mostly the two eye rasters at ~6.7 ms per frame) and rendering + flush ~35 %; esp_timer task 5.8 %; Wi-Fi task 2.5 %; idle 2 %.

**Findings**:
- Nothing busy-waits: `wait_for_flushing` is ≤ 0.07 % of core 0 (#45); loops that wait use `vTaskDelay`.
- The esp_timer task runs ~1.5 k callbacks/s (LVGL tick 1 kHz, knob 333 Hz, button 200 Hz): 4 % of a core idle-working, 6 % chasing. Moved to core 1 with `CONFIG_ESP_TIMER_TASK_AFFINITY_CPU1` (behind IDF's `ESP_TIMER_SHOW_EXPERIMENTAL`). The callbacks use atomics, a spinlock (knob/button) and `esp_wifi_connect` (reconnect timer), all cross-core safe. The esp_timer ISR and the Wi-Fi MAC ISR (`esp_wifi_init` runs from `app_main`) stay on core 0. Not done: `lv_tick_set_cb` with a slower adapter tick, longer knob/button poll periods.
- The Wi-Fi task defaulted to core 0 next to LVGL (2-3 %); now core 1 with the other network tasks. lwIP `tiT` stays unpinned.
- `sys_evt` is pinned to core 0 by IDF; its handlers are short and rare.
- The LVGL task stack had ~400 B left at its high-water mark with 8 KB (C1-C3 builds; 236 B with LVGL's OS layer on; not measured on 0.9.9). The end-of-stack watchpoint covers only the last 32 B, so 0.9.11 raises it to 10 KB: 2488 B left after a 60 fps chase and a snapshot.

**LVGL draw units (tried, rejected)**: `LV_USE_OS` FreeRTOS, `LV_DRAW_SW_DRAW_UNIT_CNT` 2, draw thread priority 4, thread 0 pinned to core 0 and thread 1 to core 1 (a `--wrap` of `lv_thread_init`, since LVGL's FreeRTOS layer creates unpinned tasks). The adapter supports it for SPI panels (it only refuses PPA with more than one unit). Thread-safe for our callbacks: the glint A8 image, label and eye canvases are written only in the LVGL task between refreshes, and LVGL finishes each stripe's draw tasks before the next timer runs. But LVGL 9 never splits a task; it only runs non-overlapping tasks in parallel, and our tasks (outline image, eyes, glint, label) overlap, so the threads mostly wait on each other. Rendering cost rose (OS sync), fps fell (50 → 47), each 8 KB draw stack is internal RAM (free 98 → 81 KB, boot minimum 64 → 45 KB). With the app offload too (C3) core 0 was 86 % against 81 % without.

## QSPI 80 MHz panel link (#23, 2026-10-05, user-approved)

- Panel IO at 80 MHz (out of the CO5300's 20 ns write spec). Knob setting `display.fast_link` (default on, Ember#283); the knob reboots to apply a change (the SPI device clock is fixed at creation). A link check (`main/panel_check.c`) writes the brightness (0x51) one LSB off and back at the link clock and reads it (0x52) over a 5 MHz 3-wire read on SIO0 (CS by hand), at boot and every 5 s. Since 0.9.35 the LVGL task runs the check between frames for the `link` task (which waits up to 1 s) and holds brightness requests until the check has restored the level, so no sample is skipped for a dimmer write. A mismatch at boot, or two in a row later, reboots at 40 MHz (RTC flag, honoured only after its own software reset: a power-on retries 80). The checkin reports `link_mhz` and `link_fallback`; the app shows "Display link". GRAM readback (RAMRD 0x2E) returns a constant 7F 00 00 here, so pixels cannot be checked.
- Measured (live server, bot page, working): full-screen refresh 34.6 → 24.8 ms; frame max in working 44-52 → 15-22 ms (glance leans move the whole outline: DMA-bound); pose refresh avg 8.5 → 8.2 ms; glint refresh 4.1 ms both (render-bound); core 0 unchanged (28-30 %). An eye area (~14 KB) is on the wire 0.7 → 0.35 ms, halving the window in which a refresh can tear.
- 12 min soak (12 chases, 13 page cycles bot → now playing → bot, demo session every 10 s): 192 checks, 0 mismatches, 0 SPI errors, no reset; frame max 35-38 ms. Internal RAM −4 KB (the 3-wire SPI device).
- Firmware 0.9.2.

## Wi-Fi link (#21, 2026-10-05)

- **HT20** (`esp_wifi_set_bandwidth`, before start): the AP gave HT40 (`40U`) at −75..−85 dBm; now `BW20`.
- **Scan**: the boot attempt and the first two reconnects after a drop are a fast scan from the AP channel (`wifi_ch` in the `cinder` namespace, written from the ember task only when it changes, dropped when the SSID changes; after boot the live channel of the last association; no BSSID or channel lock); without a hint and from the third reconnect, `WIFI_ALL_CHANNEL_SCAN` + `WIFI_CONNECT_AP_BY_SIGNAL` + `failure_retry_cnt` 2 (`wifi_scan_all_channels`, host-tested). An all-channel scan costs ~2.4 s at boot (11 active + 2 passive channels); measured with it on every boot, boot → IP went 1.7 → 4.1 s, hence the hint. Country: driver default (`01`, policy auto: it takes the AP's). No roaming (no 11k/v, no RSSI-triggered rescan): on a mesh the knob stays on the node it joined until a drop. `failure_retry_cnt` makes the driver retry internally, so `disconnects` counts events, not tries.
- **Driver storage `WIFI_STORAGE_RAM`** (set before `esp_wifi_set_config`): the reconnect scan changes and the boot config never rewrite `nvs.net80211`; its old copy stays as it was. Factory / Wi-Fi reset still runs `esp_wifi_restore()`.
- **Backoff**: 1, 2, 4, 8, 16, 30 s with ±25 % jitter, [22.5, 30) s at the cap (`wifi_backoff_ms(attempt, esp_random())`); the first retry after a transient drop (203/205/4/5/17 association, 201 not heard, 200/34/6/7/23 link lost, 8 own leave) after 250 ms (`wifi_reconnect_ms`).
- **Telemetry**: checkin `wifi` object (sorted keys, unknowns left out): `bssid`, `channel`, `disconnects` (since boot), `last_reason`, `rssi_min` (lowest since the last good checkin: samples at checkin/stats/USB status, disconnect RSSI, and `WIFI_EVENT_STA_BSS_RSSI_LOW`, armed at −80 after each IP/checkin and re-armed 3 dB below each event so it tracks the minimum without a storm). Ember ignores unknown checkin keys (non-strict decode); storing/showing them is Ember-side work. Beacon timeouts are logged and counted. Stats log adds `wifi: RSSI, min, channel, disconnects (last reason), beacon timeouts`.
- **Power save stays `WIFI_PS_MIN_MODEM`** (AP DTIM 1). ## Vertical swipe between pages (#57, Ember#315, 0.9.15)

- User decision (2026-10-06): vertical swipes. Swipe up = next page, swipe down = previous, in the enabled page order. Wraps like push and turn; both use `ts_page_step`.
- **Detection**: the screen's `PRESSED` / `PRESSING` / `RELEASED` / `PRESS_LOST` events give the LVGL indev point (CST820, read by the indev timer every 16 ms, see "Lift reporting" below) to a pure classifier, `components/cinder_cfg/touch_swipe.c` (host tests: `test/host/test_swipe.c`). Rejected options:
  - `LV_EVENT_GESTURE`: LVGL decides the gesture during the move. It resets the sum after any read that moves less than `gesture_min_velocity` and uses one fixed distance. It has no tap decision and no circle gate.
  - The CST820 gesture byte: the vendor driver reads it (byte 1 of the 15-byte frame) and drops it. Datasheet V1.2 (in the managed component) documents no gesture codes or thresholds, so they cannot be tuned for this glass. Using it means forking the managed driver.
  - Neither option was measured side by side on the knob (this change was not flashed).
- **Thresholds** (466 px over 38.2 mm of glass, ~12.2 px/mm):
  - Tap: every point stays within 20 px (~1.6 mm) of the press.
  - Swipe: starts inside the visible circle (r 233 around 236,233), ends ≥ 60 px (~5 mm) up or down, within ~34° of vertical (|dy| ≥ 1.5 |dx|), released within 0.8 s.
  - Anything else does nothing (short drag, diagonal, horizontal, out and back, slow drag). A tap outside the circle still counts, as before.
  - Guards: a press is cancelled (no push, no page, until the next press) when it gets no new controller report for 150 ms (`TS_STALE_S`, also between two reports), or when it jumps between two reports by more than max(120 px, 8 px/ms x the gap). The jump limit scales with the gap, because during a 60 fps chase an overrunning frame can push indev reads 32-40 ms apart. A real flick of 3.75-4.7 px/ms then moves 150-190 px per read (host tests: 300 px at 4.7 and 3.75 px/ms with 32 and 40 ms gaps stay swipes). After a read with no new report (more than 8 ms after the last one, `TS_MISS_S`: the finger was not seen), the limit drops back to 120 px. So a missed lift can never turn two taps (y=150, then y=300) into a swipe, over a lift gap with reads (host test, 100 ms) or one longer than 150 ms without reads. Not covered: an LVGL stall shorter than 150 ms that hides both the lift and the next landing. No read sees the finger gone, so the hardware gives nothing to tell it apart.
- **Lift reporting** (read in the code, not on the knob):
  - `esp_lvgl_adapter` in IRQ mode (INT on GPIO4) reads the CST820 only after an INT (`esp_lv_adapter_input_touch.c`, `should_read` from a semaphore the ISR gives). Between INTs it returns the cached point and state. So a lift is seen only if the chip pulses INT for it, and the next INT after a missed lift continues the old press at a new point.
  - Datasheet V1.2: the chip raises IRQ "only when a valid touch needs to be reported"; it does not say whether a lift counts. It enters standby 2 s after the last touch. The vendor driver reads the finger count from byte 2 of the frame.
  - Weak evidence that lifts do pulse INT: before 0.9.15 a touch counted on PRESSED, and a stuck press would have suppressed every later PRESSED; no such failure is recorded in these notes. Not proven: one missed lift INT would have gone unnoticed.
  - Fix in the BSP copy (`tp_read`, `tp_isr`): the indev read callback is ours. It reads the CST820 after an INT and on every read (16 ms) while a finger is down, until the chip reports zero points; a read error counts as a lift. So a lift is always seen within one read, whatever the INT does. Cost: one 15-byte I2C read at 400 kHz (~0.5 ms, on the LVGL task) per 16 ms while touched, none while idle. The time of the last read with a finger (`bsp_knob_15_md50et_touch_report_us`) drives the stale guard.
- **Tap vs swipe**: the tap is decided on release, so a swipe never also fires a push. The tap's push comes later by the contact time plus at most one indev read (16 ms).
  - A longer press delays its push by the hold.
  - With `swipe_pages` off, the press counts at once again, as before 0.9.15. The wipe and dots stay on for push and turn (intended).
  - On Now Playing the dimmed face wakes on press again (a counter bumped on `PRESSED`, read only on that page), so a drag, a diagonal or a long hold wakes it at once. A wake never pushes.
- **Transition**: a 180 ms soft wipe on the top layer for every page change (swipe, push and turn, dev tool). The redraw rows and the mirror for "previous" are pure (`ts_wipe_span`, `ts_wipe_rows`), host-tested in both directions with clipping.
  - The new page shows at once under a black curtain. The curtain's edge has a 32 px band that fades in 2 px rows. It moves up for next and down for previous, with an ease-out.
  - One full-screen object with a draw callback, no buffer. Each 16 ms frame invalidates only the rows the edge passed plus the band: 11 frames, largest strip 117 rows (55 k px, host). The page switch itself still redraws the full screen once, as before.
  - Rejected: sliding the page roots (`translate_y` invalidates all 472x466 every frame, ~25 ms of DMA each at 80 MHz, so ~5 fps for 200 ms); an opacity fade (a full-screen LVGL layer each frame); a panel brightness fade (the link check reads 0x51 back and the dimmer owns it).
- **Page dots**: 8 px dots, 16 px pitch, in a column at x 442-450 (r ~210, inside the Pomodoro ring). The current page is white, others grey. Created on a change and deleted 1 s after the last one, so they hold internal heap only for that second. A page-list change from Ember while they show rebuilds them with the new count.
- **Setting** `swipe_pages`: a top-level bool. Absent = on, like Ember's other flags; a non-bool is ignored. The Ember side is Ember#315 (server key plus a toggle in the app's Pages section).
- **Dev tool**: CINDER1 `{"op":"input","input":"swipe_up|swipe_down","n":1-3}` feeds the same counter as a touch swipe and is ignored with `swipe_pages` off. Shortcut: `input.py swipe_up`.
- **Cost**: static internal +72 B (`.bss` +56, `.data` +16; the classifier state is in PSRAM; no IRAM change: the INT flag is a 32-bit atomic, since 1-byte atomics pull `__atomic_*_1` helpers into IRAM). Image +2,648 B (1,639,711 → 1,642,359). The wipe object holds ~0.1 KB of internal heap (LVGL objects use malloc, and small allocations land in internal RAM); the dots hold ~0.5 KB for 1 s.
- **Not measured on hardware**: frame time and CPU during the wipe (the refreshes count as "other" in the 30 s stats log), real tap contact times, the CST820 report rate and whether it pulses INT on a lift, and the thresholds by hand. After a flash, measure with an `input.py swipe_up` loop, diagnostics full, and real swipes.

## Secret-free builds (0.9.16, user decision 2026-10-06)

- No build carries a secret. `CMakeLists.txt` layers `sdkconfig.secrets` only with `-D CINDER_SEED_SECRETS=1` (opt-in dev seed, own build dir); `CONFIG_CINDER_WIFI_SSID/PASSWORD` and `CONFIG_CINDER_EMBER_URL` `depends on CINDER_DEV_SEED`, so they are not even in `sdkconfig` otherwise. `CONFIG_CINDER_EMBER_TOKEN` is gone: the dev seed never wrote a device token, only the master token. A dev-seed image keeps the marker `CINDER-DEV-SEED-BUILD` as a used const read once at boot (not a log string, so a log level can't drop it); Ember refuses it on upload (`dev_seed_build`) and `secret_scan.py` checks it. The build stops (CMake) when `sdkconfig` has `CINDER_DEV_SEED=y` without `-D CINDER_SEED_SECRETS=1`, so a stale `sdkconfig` can't compile secrets in.
- **Token**: a token counts only together with a device id (`cfg_paired`, host-tested). At boot a `dev_tok` is erased from NVS only when reading `dev_id` gives a definite `ESP_ERR_NVS_NOT_FOUND` (`cfg_drop_token`, host-tested; any other read error keeps it); only the `dev_tok` key is erased, nothing else is rewritten (log `token without a device id removed from NVS: not paired`). `config_store_token` returns nothing unless paired, and `http_conn` then sends no `Authorization` header. Unpaired knob: "Not paired" label, Pomodoro note `NOT PAIRED`, no Pomodoro or now-playing commands, no checkin; it still reads the unauthenticated legacy endpoints (`/state`, Pomodoro and weather state, brightness). A paired knob (`dev_id` + device token in NVS, the live knob) is unchanged by an app-flash.
- Code paths that read the token, checked: `http_conn` (bearer for POST/PUT and view GETs), Pomodoro actions (`pomo_client`), now-playing commands, checkin and core dump upload (device only), view polling (device only, `view_policy`). Weather, `/state`, Pomodoro state and brightness reads never sent it.
- **Check**: `tools/secret_scan.py <bin> <elf>` looks for every string value in `sdkconfig.secrets`, `EMBER_TOKEN` from `~/.config/ember/producer.env` and the dev-seed marker; prints names and booleans only; `build_release.sh` and `publish.sh` run it. Host-tested (`test/tools/test_secret_scan.py`, run by `test/host/run.sh`): each source of secrets, escaped values, the marker, empty and non-string values, and that no value is printed. 0.9.16 default local build (`idf.py build`) and `build_release.sh`: all absent. The 0.9.15 local build (secrets layered automatically): Wi-Fi SSID, password, URL and token all present.

## OTA from Ember (#10, Ember#225, 0.9.16)

User decisions (2026-10-06): upload only (Ember never contacts GitHub); Ask first per knob (Automatic opt-in, `release` channel, idle 10 min); rollback after 30 min without a good checkin; input ignored during a download, no cancel; signed images later (non-goal); one-time USB bootloader flash after review; hardware tests on the live server, never repointing the knob.

- **Bootloader**: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`, no anti-rollback (it burns eFuses), `CONFIG_BOOTLOADER_PROJECT_VER=2`. The app reports `ota.rollback` only when the app itself is built with rollback and the bootloader description (`esp_ota_get_bootloader_description`) says version ≥ 2 (`ota_rollback_capable`); Ember offers nothing without it. An app built without rollback writes `UNDEFINED` instead of `NEW` on `set_boot_partition` (no rollback at all), so `ota_client.c` has an `#error` and `main/CMakeLists.txt` stops the build for a `sdkconfig` without rollback or with `BOOTLOADER_PROJECT_VER` < 2. The new bootloader is 20,032 B (19,952 before; 12,736 B left below the partition table at 0x8000). It takes effect only with the one-time `idf.py flash` (`workflow.md`); partition table bytes unchanged (SHA-256 `dbcebbd6…` before and after).
- **Checkin** (keys sorted): `fw_build` (first 4 bytes of `app_elf_sha256` as 8 hex, the running app's), `ota` = `{"image":"valid|pending_verify|new|undefined","last":{"attempt","error","result","version"},"phase":"idle|waiting|rebooting","rollback":bool,"slot":0|1}`, `diag.crash.elf` (8 hex from the core dump summary). `last` lives in NVS until a new attempt starts and carries the offer's `attempt` (Ember ignores a `last` without it, and mints the next id as max(its counter, `last.attempt`) + 1). Lasting declines report `{"result":"failed","error":"refused"}` for that offer's attempt, once: the bad-image guard and the per-boot cap. Transient waits (Pomodoro, input not idle, backoff, not ready) report nothing. Body buffer 1280 → 1536 B (PSRAM).
- **Offer** (checkin reply `ota`, `ota_offer_parse`): `attempt` ≥ 1, `build` 8 hex, `sha256` 64 lower hex, `size` 288 B..4 MiB (and ≤ the slot), `version` strict semver, `url` exactly `/v1/devices/self/firmware/<version>` (the knob uses its stored Ember URL; anything else is ignored), `auto`, `retry`.
- **Start** (`ota_start_decide`, on the ember task after the checkin that carried the offer): rollback bootloader, running image `valid`, Wi-Fi, paired; refuse when `sha256` = NVS `ota/bad` (cleared by `retry:true`) or after 3 started attempts of that attempt id this boot (Ember's Retry is a new attempt and goes at once); wait while a Pomodoro runs or is paused, for an `auto` offer until 10 min without knob input, and in backoff (1, 5, then 30 min after a failure; reset by a new SHA or `retry`).
- **Download** (`main/ota_client.c`, `http_conn_stream`): `GET` on the ember task's kept-alive connection with the device token, read in 4 KB pieces into one 4 KB internal DRAM staging buffer (PSRAM fallback, logged), streaming SHA-256 (mbedtls, HW SHA), `esp_ota_begin(next, OTA_WITH_SEQUENTIAL_WRITES)` (4 KB sector erases as data arrives), `esp_ota_write`. The first 288 bytes are checked before the first write: image magic, chip 9, app desc magic, project `cinder`, version and build (`app_elf_sha256` prefix) = offered, IDF major = the bootloader's (`desc`). The offer is copied when the attempt starts, so nothing later changes the pinned values. `alive()` per piece, `vTaskDelay(1)` every 64 KB. Network error or 5xx: up to 3 resumes (5, 15, 30 s) with `Range: bytes=<written>-` and `If-Range: "<sha256>"`; a 206 must start at `written`, a 200 restarts from 0 (`esp_ota_abort`, begin again). 5 min cap per attempt (`net`). Then size, SHA-256 (`sha256`, image blocked), `esp_ota_end` (`image`, blocked).
- **Switch**: a plain view poll for a fresh Pomodoro state. Pomodoro running or paused: `phase:"waiting"`, normal UI, boot slot untouched, checked each loop pass. The verified image is recorded as `att_state=ready` (a reset while waiting reports `failed/reset_waiting`, not blocked; until 0.9.37 the load dropped `att_state=3`, so the knob forgot the attempt instead). Else NVS `att_state=boot` first, then `esp_ota_set_boot_partition` (a failure reports `failed/flash`), checkin with `phase:"rebooting"`, "Restarting" on the face, `esp_restart()`.
- **First boot** of the new image (bootloader: `NEW` → `PENDING_VERIFY`; any reset before the mark → `ABORTED`, old slot): mark valid at the first `200` checkin with uptime ≥ 60 s, at least one rendered frame, one good view poll and the health gate passed (`ota_valid_ready`, health gate below); 3 failed marks roll back (`mark_valid`). No such checkin within 30 min: `last={rolled_back,no_checkin}` (or the first failing health reason when a checkin succeeded, below), `esp_ota_mark_app_invalid_rollback_and_reboot()`, deferred up to 60 min more while a Pomodoro runs; if the rollback call fails it is retried after 1, 5, then 30 min, and NVS is written only when the record changes. A power cut after the boot slot was set boots the new image, which verifies and reports `ok`. The old image after a rollback finds `att_state=boot` and its own last invalid partition holding the attempt's build (read only in that case: `esp_ota_get_last_invalid_partition` hashes the whole slot, so later boots skip it); another image there means `interrupted`: `rolled_back/boot` unless a `no_checkin` record is there; `att_state=dl` at boot = `failed/interrupted`. A rolled-back image is blocked (`ota/bad`) until Ember's `retry`.
- **Health gate** (#1, 0.9.29): while the image is pending verification, marking it valid also needs `ota_health_check` (`components/ota_policy`) to pass. Checks, in order, each with its rollback reason (all match `^[a-z0-9_]{1,24}$`, so `ota.last.error` carries them):
  - `health_display`: the panel link check (`link_task`) completed at least once without a confirmed failure at the 40 MHz clock. No completed check yet (all errors) is pending. The check runs on the LVGL task and `link` waits 1 s for it (until 0.9.33 it took the LVGL lock with a 1 s timeout), so an LVGL task stalled before the first completed check leaves the link pending, and the deadline rolls back with `health_display`, not `health_render`. A confirmed failure at 40 MHz (boot: one check plus 2 of 3 rechecks; soak: two in a row, the same rule as the 80 MHz fallback) is a **hard fail**: `ota_client_service` rolls back at once, before the deadline and even before a checkin. A failure at 80 MHz is not a gate failure: its fix is the 40 MHz fallback reboot, held until the image is valid. The mapping is `ota_link_result` (host-tested). Known cost: the hard fail is about the hardware, not the image. A knob that is already on 40 MHz (`fast_link` off or the fallback active) and fails the check there confirms it at boot on every new image, so every update rolls back with `health_display` and is blocked (`ota/bad`) until Ember's retry, though the old image runs on the same panel. By design the hard fail also ignores the Pomodoro deferral and the 60 s rule ("at once"). Marking valid re-reads the link state right before the otadata write and refuses on a fail, so a fail noted between the health snapshot and the mark cannot be accepted (Codex P1 on #6).
  - `health_render`: ≥ 20 refreshes since boot that had pixels to draw (`refr_cb` counts a `LV_EVENT_REFR_READY` only when the refresh had invalidated areas; `REFR_READY` also fires for empty runs) and the 16 ms `frame_cb` LVGL timer ran in the last 30 s (`ota_client_note_loop`, called in `frame_cb` before the OTA face, reset and setup early returns; only the `no_render` and `lvgl_stall` test faults return before it). This proves LVGL rendered and handed areas to the flush; flush errors and a dark panel (bad init, brightness never set) are not seen, only the link check talks to the panel. A "frame in the last 30 s" rule was rejected: LVGL refreshes only after an invalidation (`lv_display_refr_timer` pauses itself), and an idle or sleepy bot, a static page (weather, a paused Pomodoro, now playing paused), the OTA face or setup can go more than 30 s without one. The ~750 refreshes per 30 s baseline was measured in the "working" mood only. Checked: no code path stops the LVGL timer handler. Dimming, night levels and brightness 0 only write the panel's brightness register. Since 0.9.35 the ember task only queues the level (`panel_check_brightness`, never blocks) and the LVGL task writes it, so a stalled LVGL task cannot block the ember task: it keeps checking in, and the deadline rolls back with `health_render` instead of the ember watchdog resetting the knob (Codex P2 on #6; the 90 s ember watchdog still fires if the ember task itself hangs). A level queued during a stall is written when the LVGL task runs again (until 0.9.33: a 1 s lock wait per step and `dim_fade_retry` with a 5 s hold); the adapter's auto sleep is off (`ESP_LV_ADAPTER_DEFAULT_CONFIG`) and nothing calls `esp_lv_adapter_pause` or `sleep_prepare`; USB quiet mode only lowers log levels.
  - Input is **not** gated (user decision 2026-10-08, after review of #6): no passive input signal is both cheap and independent. The indev callback runs every 16 ms but reaches the CST820 over I2C only after an INT, while a finger is down, and once at start, and the chip enters standby 2 s after the last touch; `iot_button` and `iot_knob` keep their poll timers private. A gate on the start read alone could roll back a good image if that read failed. The counters stay and are logged with every gate state change: successful CST820 reads since boot (`bsp_knob_15_md50et_touch_ok`) and whether a real turn or press happened (`ota_client_note_input`).
  - `health_heap`: since-boot minimum free internal heap ≥ 27 KB and minimum largest internal block ≥ 15 KB (`diag_health`; the largest block is sampled at checkins, every 30 s and at boot).
  - `health_stack`: stack high-water mark ≥ 1024 B for `lvgl`, ≥ 512 B for every other task in `diag.c` `TASKS[]`.

  Limits are the `OTA_HEALTH_*` constants in `components/ota_policy/include/ota_policy.h` (one place, host tests use the names), about half of what 0.9.28 measured: heap 27 KB from the lowest internal free heap since boot, 54 KB on the knob running 0.9.28 (Ember app, `diag.heap_internal_min`); largest block 15 KB from about 30-31 KB (the app's documented example ~30 KB, the 0.9.28 log 31 KB); LVGL stack 1024 B from 2,484 B headroom in the 0.9.28 log. The 512 B floor for the other tasks is a margin, not a measured half. Outcome (`ota_verify_rollback`): a hard fail rolls back at once with `health_display`; at the existing deadline (30 min, 2 min in a test build, Pomodoro extension kept) a knob whose checkins succeeded rolls back with the first failing reason; a knob that never had a `200` checkin, or that is healthy but still not valid, keeps `no_checkin`. The knob logs the gate state when it changes (`health pending: health_render (...)`, `health pass (...)`, with the input counters). Firmware cost: counters only (frames, last `frame_cb` tick, successful touch reads (logged only), link state, checkin seen, the USB mark request), the gate input in the PSRAM OTA state, no new task; image +2,484 B.
  - **Override**: CINDER1 `{"op":"ota_valid"}` (every build; `tools/ota_fault.py valid`) marks the pending image valid, skipping only the health checks: it still needs a `200` checkin this boot, 60 s uptime, a frame and a view poll (`ota_override_check`). The USB task only checks the preconditions and posts the request; the ember task (6 KB stack, where the checkin mark already runs) does `esp_ota_mark_app_valid_cancel_rollback`, `ota_rec_valid` and the NVS write on its next loop pass (woken with `ember_client_wake`), and the USB task replies when it is done, so the otadata write never runs on the 3.5 KB `prov` stack and every mark and rollback is on one task. Replies: `ok`; `not_pending` (image not pending verification); `no_checkin` (no `200` checkin this boot); `not_ready` (60 s, frame or view poll missing); `busy` (another `ota_valid` is running, or the ember task did not take the request within 25 s). A pending request (`ota_client_mark_pending`) ends a long-poll at the next idle slice (≤ 1 s) and the wait between polls (checked at least once a second), with or without the wake eventfd (#7; before, a knob without it could answer `busy` during a long-poll). Only those two waits are cut short: while the ember task is in another request (a plain view or state GET, a checkin, a now-playing art fetch, a core dump upload) the request is taken when that one ends, within the 25 s budget; `failed` (the otadata write failed, or the link failed at 40 MHz and the rollback is due). The reply can take up to ~30 s; `ota_fault.py valid` waits 35 s.
- **LVGL liveness watchdog** (#7, 0.9.31): a valid image no longer gets the incidental reset (an LVGL task stuck holding the lock used to block the fade, then trip the ember watchdog). `frame_cb` counts its ticks (`s_loop_ticks`, next to `ota_client_note_loop`); the stats task checks the count every `STATS_PERIOD_MS` (30 s), and `LVGL_STALL_CHECKS` (2) checks in a row without a tick (60-90 s stalled) log `LVGL loop stalled` and `abort()`. Skipped while the image is pending verification (the health gate owns that window: `health_render` or `health_display`, and a reset there would be a bootloader rollback without a reason) and while the OTA face is requested. If the rollback itself fails (`ESP_ERR_OTA_ROLLBACK_FAILED`, retried after 1, 5, then 30 min), the image stays pending, so the watchdog stays off for the rest of that boot. No timer or task: a counter in `frame_cb` and a compare in the stats task. False positives need `frame_cb` itself to stop for a minute: the adapter's auto sleep is off and nothing pauses the LVGL timer handler (health gate notes above).
  - **Attribution**: before the abort, an RTC_NOINIT note (`dev_stall_note_t` in `diag.c`, magic-guarded like the TWDT culprit note) is marked. On the next boot, a `panic` reset with the mark reports `reset_reason` `lvgl_stall` in `diag` and `stats`. A core dump is written only when the coredump partition is empty (`CONFIG_ESP_COREDUMP_FLASH_NO_OVERWRITE`). Then that dump's `diag.crash` is `{"reason":"lvgl_stall","task":"lvgl"}` (`dump_rr` 0x40 in NVS; the dump's own task is `stats`, where `abort()` ran, and every task's backtrace is in it). If an older dump is still waiting for upload, no new one is written: `diag.crash` keeps describing the old dump, and only `reset_reason` shows `lvgl_stall`. Both fields fit Ember's checkin schema (`diag.reset_reason` and `crash.reason` `^[a-z0-9_]{1,24}$`, `stats.reset_reason` `^[a-z][a-z0-9_]{0,15}$`); the macOS app shows unknown reasons raw.
  - **Restart-loop guard** (`dev_stall_boot`, `dev_stall_check`, host-tested): the note counts consecutive stall resets. A `sw` reset (USB reboot, OTA restart) keeps the count; any other reset, including a panic without the mark, clears it. After `DEV_STALL_MAX_RESETS` (3) stall resets in a row the watchdog only logs (`not restarting`). A boot that runs `DEV_STALL_CLEAR_MS` (10 min) without a stall clears the count and re-arms the watchdog in that boot. So a stall that repeats on every boot costs three restarts (about 3-5 min), then the knob stays up with a frozen face: it still checks in, so a fixed image can arrive over the air.
- **Stack floors** (`OTA_HEALTH_STACK_MIN` 512 B) for `eye`, `stats` and `prov` are a margin, not measured. The 30 s stats log prints every tracked task's high-water mark on one line (`stack free B: ember 1880, eye 900, ...`, `diag_stacks_line`, the `diag.c` `TASKS[]` order; `TASKS[]` is `char[][8]` and `IDF_TASKS[]` `char[][10]`, each name checked at compile time so one with no room for its NUL (8+ or 10+ characters) does not build; another `_Static_assert` checks the worst case, every task with a 10-digit value, against `DIAG_STACKS_LINE_MAX` (184 B; 344 B since 0.9.32, which appends IDF tasks after `| idf`), so the line cannot be cut; it replaces the LVGL-only and one-time stats-task headroom lines) so the floors can be measured over USB on a release build; floors unchanged until then. Cost of #7 (fade retry, `ota_valid` wake, watchdog with its restart-loop guard and attribution, stack line): image 1,674,727 → 1,675,731 B (+1,004), DIRAM `.bss` +224 B (mostly the 184 B line buffer, static to spare the 3 KB stats stack), RTC slow memory +16 B (the stall note).

## Task stacks and internal RAM (GitHub #10, 0.9.32)

Goal: size every task stack from its worst case, cut internal RAM waste, never trade away safety. Rule: at least 1 KB over the measured or estimated worst case for every task, 1.5 KB for `lvgl` and `ember`. All figures below are **estimates** from a static model, not proven bounds, and nothing is measured on hardware yet; the paths to exercise are at the end.

**Method.** `firmware/tools/stack_walk.py build/cinder.elf [task …] [--path]` (config `tools/stack_walk.json`) walks the call graph from each task entry and prints, per task, the estimate, the configured stack, the margin and the **indirect call sites** it reached that it cannot resolve statically (counted as 0 B): `unresolved` in functions with no pointer-table entry, `tabled` in functions with one (assumed covered by the listed targets, not checked). A long call whose literal is not a function counts as unresolved, not as no call: mostly a null-guarded call to an undefined weak hook (`tlsf_free`, `tlsf_realloc`, `esp_startup_start_app`), else a register the linear scan carries across a branch join (`listener_task`, `esp_wifi_register_if_rxcb`) or a symbol offset. Frame sizes come from each function's Xtensa `entry a1, N` (equal to `-fstack-usage` for compiled code; it also covers the precompiled Wi-Fi, newlib and ROM code, read from the ROM ELF in `~/.espressif/tools/esp-rom-elfs`). Calls: `call8`, `call0`, and the `l32r` + `callx8` long calls (most calls in a 1 MB image); a register loaded by `l32r` counts as overwritten by any later instruction that writes it (only stores, branches, calls and special-register writes keep it). **Decoding** (GitHub #15): `objdump -d` sweeps each function linearly and loses sync after an unconditional jump followed by alignment padding: it decodes the padding plus the start of the next real instruction as one garbage instruction, so a real call can vanish, and what it decodes depends on the link layout (`l32r` offsets are PC-relative). The tool now walks each function from its entry along fall-through, branch, loop and `jx` jump-table targets. A table counts only when the `jx` register traces back through `l32i reg, x, 0` ← `addx4` (or `slli i, 2` + `add`) ← the `l32r` of the table; an unrelated literal in between is ignored. The table also needs an unsigned bound check on the index on the way in (`bltui`/`bgeui`, or `movi` + `bgeu`/`bltu`), which gives its length; every entry up to that length (at most 1,024) must land in the function. The bound check must be the only way in: the trace goes back only through instructions with one known predecessor, a loop body start or a table case counts as having an unknown predecessor, and tables are traced again once the walk has found every branch. The table is read from the ELF. A target the sweep decoded inside another instruction is disassembled again from that address (`objdump --start-address`). Bytes this walk never reaches (padding, garbage, C++ landing pads) are not scanned. A call there to a symbol start (`call8`, or `l32r` of a function + `callx8`, the `l32r` possibly in the reached code just before) counts as unresolved; any other is dropped as decode garbage. A function with a `jx` whose table it cannot trace or read keeps its whole sweep. A `jx` straight from an `l32r` of an instruction-bus address (the ROM `__call_*` thunks, e.g. `esp_rom_printf`) is a tail-call edge, and so is a branch or `j` to another function's start. A branch into another function's middle (ROM libgcc float helpers share code) is an edge to that whole function, which over-counts its frame. A target the re-disassembly still can't decode, or a branch that lands in no function, counts as unresolved on its function. A `call8`, or an `l32r` + `callx8`, to `<sym+0x..>` past the symbol's `nm` size goes to a stripped static function (Wi-Fi blob). It is decoded as an anonymous function; every other `entry` in that gap that the walk doesn't reach starts a sibling anonymous function. A call to `<sym+0x..>` inside a function counts as unresolved. The tool prints these counts; 0.9.37:
- 5,768 targets re-disassembled, 2 left undecoded; 12 functions kept whole.
- Branches into other functions: 62 edges, 3 unresolved.
- 528 `<sym+0x..>` calls in the sweep. In reachable code, 109 go to anonymous functions and 3 are inside a function; the rest are in bytes the walk never reaches.
- 34 unreachable calls to a symbol start; 286 dropped.

A `-fstack-usage` scratch build found no unbounded dynamic frames in app code (9 `dynamic` frames in IDF: touch point VLA, `spi_flash_mmap_pages`, I2C, ADC, heap init; none on a deep path). Assumptions, all in the JSON:
- **Function pointers** resolve only through listed edges: LVGL timers (`frame_cb`, refresh, indev, anim), event classes in use (obj, label, image, arc) and the app's callbacks, the SW draw unit, draw-buffer, font, bin-decoder and cache handlers, the adapter flush, `tp_read`; HTTP (`on_event`, parser callbacks, `alive`, `coredump_read`, `dl_sink`, OTA ctx callbacks), transport (TCP only: the Ember URL is http only), flash chip and HAL drivers, NVS partition I/O, cJSON hooks; logs go `vprintf` → USB-Serial/JTAG. Any event callback may call any other in-use one. The rest stay unresolved (unresolved / tabled per task, with the checkin `config` depth check: ember 227 / 216, lvgl 140 / 59, prov 170 / 146, reset 146 / 135, stats 105 / 14, pomo 53 / 63, weather 53 / 63, link 15 / 14, orbit 1 / 0, rim 0 / 0, eye 0 / 0; mostly NVS C++ vtables, newlib stdio hooks, Wi-Fi blob ops, LVGL cache/anim/decoder ops, SPI and GDMA HAL).
- **Infeasible edges cut**: argument-check error logs that cannot fire (`esp_cache_get_alignment`, `esp_mmu_vaddr_to_paddr`); `__kernel_rem_pio2` (only for |x| > 2^19·π/2; our angles are a few turns); logs inside flash-driver code (cache off, they take the ROM printf path); `__sbprintf` (stdout is line-buffered, newlib only uses it for unbuffered streams); `abort`/`assert` paths (fatal anyway), including `assert_valid_block` → ROM `ets_printf` (heap-corruption report before `abort`, reachable since the tail-call edges of #15).
- **Recursion and cycles**: a path never repeats a function; a result is cached only when no cut depended on a caller further up, so a node reached from another ancestor is recomputed (the earlier version cached it and could under-count); a cached result is reused only when its worst path shares no function with the current path, else it is recomputed (before, a reused result could repeat a function: `main`'s 5,728 B path ran nine LVGL layout functions twice). The path to a recursion cycle head uses the same rule (before, its cache could under-count); it is then joined with the head's own worst path without checking for shared functions, which can only over-count. Seeded brute-force tests check both walks against exhaustive search on small random graphs. `--path` prints the path behind the reported row, with the recursion budget marked at the cycle head. LVGL event dispatch is cut at **2 entries** per path into `event_send_core` / `lv_event_send`, so a path gets one object-class dispatch plus one list or display dispatch. This is a heuristic, not a bound: any event handler can reach any other through setters, so without a cut the 74-function event cycle makes a path of the whole cycle, but a real nested object event (label `SIZE_CHANGED` → `GET_SELF_SIZE`) is cut too, because a path never repeats a function. Letting each nesting level re-run functions, with the same cut at 2, raises `lvgl` to 8,736 B (margin 1,504, under its 1.5 KB rule) and `main` to 6,064 B (margin 848, under the 1 KB rule); at 3 levels `main` overflows. Those deeper paths are judged infeasible (they repeat `lv_arc_event` → `lv_obj_draw` → drop shadow at every level, which the any-handler pointer table allows); the hardware high-water marks decide. Budgets, added on the deepest path through the cycle head: LVGL redraw 4 object levels (640 B per level; deepest tree: screen → now playing root → album circle → note label); cJSON parse and delete 32 levels (`CJSON_NESTING_LIMIT=32` for the whole build and the host tests, default was 1000; a host test checks 32 parses and 33 does not); cJSON print 5 levels: the only print is `dev_checkin_parse` re-printing the `config` block of Ember's checkin answer, and it drops (one `ESP_LOGW` per `config_version`) a `config` nested deeper than `DEV_CONFIG_MAX_DEPTH` = 4 object/array levels (the block itself is level 1) before printing, so the bound holds whatever the server or the plain-HTTP link sends (4 container levels + their scalar leaves = 5 `print_value` frames). Ember sends 3 (`knobSettings` → `pages[]` → `{id,on}`); a dropped block is not applied and the next checkin retries it (host test in `test_device.c`).
- **Fixed overhead 768 B per task**: coprocessor save area 316 B (+ alignment), the initial exception frame 192 B (`XT_STK_FRMSZ`), one interrupt frame 192 B, window base save area and slack. Calibrated on 0.9.31: the LVGL path through `tri_build` estimates 7,056 + 768 = 7,824 B, measured 7,756 B used.

### Architecture follow-ups (#12, 0.9.35)

**PSRAM stacks: `rim`, `stats`, `link`, `orbit`, and the legacy pollers `pomo`, `weather`** (`xTaskCreatePinnedToCoreWithCaps(…, MALLOC_CAP_SPIRAM)`; the TCB stays internal; `CONFIG_FREERTOS_TASK_CREATE_ALLOW_EXT_MEM=y` is the S3 default). A PSRAM stack must never be in use while the cache is off, so each task was checked for flash access (NVS, OTA, partitions, `esp_core_dump`, `spi_flash`):
- `rim`: raster into PSRAM buffers, `bot_body_ring`, `vTaskDelay`. No flash. `orbit`: table fill and `vTaskDelay`, then it sets a flag and suspends itself; the `stats` task deletes it by handle on its next 30 s tick (`vTaskDeleteWithCaps(handle)`). A self-delete (`vTaskDeleteWithCaps(NULL)`) would create a helper task with an internal stack and `abort()` if that create failed (Opus L1 on #16); deleting by handle needs no helper. Stack 3328 B (PSRAM), estimate 2144.
- `stats`: logs, heap queries, `esp_wifi_sta_get_ap_info`, `uxTaskGetStackHighWaterMark`, `diag_stall_check` (RTC no-init memory only). Its `abort()` on an LVGL stall panics on the task stack (PSRAM, cache on); the core dump then switches to its own 1792 B internal stack before it writes flash (`CONFIG_ESP_COREDUMP_USE_STACK_SIZE`, on whenever external task stacks are allowed), and `esp_restart_noos` moves SP to internal RAM before it disables the cache.
- `link`: settings copy (RAM), OTA health notes (atomics), `esp_restart` (shutdown handlers: Wi-Fi stop, timekeeping; no flash; SP moved as above) and, until the single panel owner below, the panel read over SPI (the driver bounces non-DMA buffers; cache on).
- `pomo`, `weather`: HTTP over lwIP, cJSON, `config_store` getters (RAM copies under a spinlock), atomics. No flash (call graph checked as above).
- Not moved: `eye` (frame-time check first), `lvgl`, `ember`, `prov`, `reset` (NVS or OTA).
- Internal RAM: −10,496 B of stacks in a normal run (`rim` 2560, `stats` 3840, `link` 4096), −3,328 B more at boot (`orbit`), −10,752 B while Ember has no view (`pomo` 5632, `weather` 5120). The TCBs stay internal. PSRAM +13,824 B, +10,752 B more while polling legacy endpoints. PSRAM stacks are slower than internal ones; none of these tasks is on the frame path.

**One panel and LVGL owner** (`main/panel_check.c`, pure part `components/panel_req`, host-tested in `test_panel.c`). After boot only the LVGL task takes the LVGL lock and talks to the panel; `frame_cb` calls `panel_check_frame()` first, also while the OTA test fault `no_render` freezes the screen.
- Brightness: `panel_check_brightness(level)` stores the newest level (any task, never blocks, also before `panel_check_init`); the next frame writes it. A failed write is retried every 100 ms unless a newer level arrived. The dimmer's 1 s lock wait and 5 s retry hold are gone (`dim_fade_retry` removed, and with it the BSP's lock-taking `set_brightness_level[_wait]`): if the LVGL task stalls, the newest level waits and is written when it runs again. The startup level goes the same way.
- Link check: `panel_check_run(seed, raw, 1000)` posts a ticket and polls for its result every 10 ms, at most 1 s; the LVGL task runs the loopback as steps over frames (read 0x52, write the level XOR 1 or XOR 2 by seed parity, ≥ 60 ms later read back and restore, ≥ 60 ms later read back), so it never sleeps in the LVGL task. A timeout returns -1 (counted as an error; `ota_link_result` and the fallback see nothing, as with the old lock timeout); the late check still finishes and restores the level, and its result is dropped. A newer ticket replaces one not yet started. A check starts only 60 ms after the last panel write returned (timed after the SPI call, so a write that blocks behind a flush does not eat into the settle time), because RDDISBV can lag a write (the fake panel in `test_panel.c` models that lag): without the wait, a check that starts in the frame of a dimmer step reads the old level and its restore puts the old level back. Brightness requests wait while a check waits or runs (≤ ~200 ms), so the old -2 ("dimmer wrote meanwhile") is gone. A check that fails half-way writes the old level back; if that write fails too, the old level is queued like a brightness request and retried every 100 ms (a newer level wins).
- Snapshot: `screen_snap_release()` only marks the buffer; the LVGL task frees it on its next frame, also while `no_render` freezes the screen. A new `snapshot` waits for that within its timeout.
- The LVGL stall watchdog is unchanged (`s_loop_ticks` in `frame_cb`). Estimates: `lvgl` 8368 B (the check adds 1968 B from `frame_cb`, below the render path), `link` 2704 B (no SPI on its stack).

**cJSON in PSRAM** (`app_main`: `cJSON_InitHooks` with `heap_caps_malloc_prefer(n, 2, MALLOC_CAP_SPIRAM, MALLOC_CAP_DEFAULT)`, `free`), chosen over lowering `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`:
- Scope: the hooks move only cJSON's own allocations (nodes, key and value strings, print buffers); the threshold would move every `malloc` ≤ 16 KB of the app, LVGL (`LV_USE_CLIB_MALLOC`), lwIP, `esp_http_client` and IDF drivers, and would need an audit of every plain `malloc` that must stay internal (cache off, DMA, ISR). cJSON users are all task code (`knob_view`, `device_api`, `knob_settings`, `cinder_line`, `ota_policy`, `np`, the ember, pomo and weather clients); none runs with the cache off or hands a cJSON buffer to DMA. Printed strings go to `esp_http_client` (lwIP copies them), USB (copied into the driver's ring buffer) or NVS (`esp_flash_write` copies non-DRAM sources through a bounce buffer).
- PSRAM full: the hook falls back to internal RAM, as before.
- No realloc: `cJSON_Hooks` has no realloc slot, and cJSON uses `realloc` only with the default `malloc`/`free`. With hooks a print buffer grows by allocate, copy, free (doubling from 256 B) and ends with one exact-size copy, so printing peaks at about 3× the printed size during growth and 2× at the final copy. The only print is `device_api.c` re-printing the checkin `config` block (a few hundred bytes to ~2 KB), so the peak stays a few KB and is in PSRAM unless PSRAM is full.
- Effect: every parsed view, checkin answer, settings blob and CINDER1 line now builds its tree in PSRAM. The 410 B view fixture of `test_view.c` makes 78 allocations; bigger views (now playing, hosts) scale with their size. This lowers the internal peak and churn (`heap_internal_min`, `heap_largest_min`), not the idle free figure. Parse time in PSRAM is not measured (one view per change).
- The threshold stays at 16 KB: the remaining small internal mallocs (HTTP client buffers, LVGL objects) are per-frame or long-lived; moving them needs the audit above and a frame-time measurement.

**Legacy pollers end when the view is back** (`net_policy/legacy_task.c`, host-tested in `test_net.c`). The ember task decides on every pass (`pomo_client_legacy(legacy)`, `weather_client_legacy(legacy)`): on at a fallback, off when the view returns, as before. The lifecycle is a lock-free state (gone, run, stop, parked):
- Off: the task notices within one wait (pomo: one poll period or a queued action, which it puts back for the ember task; weather: 1 s slices; a request in flight finishes first), frees its HTTP handle (it owns it) and parks (suspends itself); only after a successful park does it report its stack as gone to `diag`. It holds no lock when it parks.
- Reap: the ember task's next pass deletes the parked task by handle (`vTaskDeleteWithCaps`, no helper task), frees the weather buffers (16 KB body, connection struct; allocated by the ember task before the create), clears the stack figure and logs `legacy poll task removed`. A park that lands between the ember task's state load and its compare-and-swap is still reaped before a new task is created (host test `test_legacy_park_race`). No task deletes itself, so nothing is freed behind a reader.
- On again before it parked: it keeps polling; no second task. On after it parked: reap, then a new task. A failed create or allocation backs off 5 s, doubling to 5 min (no `assert`; Opus L3).
- Stack figures: `pomo` and `weather` report their own high-water mark to `diag` at the top of each loop and again after the poll's HTTP, parse and log work, before they wait (`diag_note_stack`; -1 once parked or removed). `diag_health`, `diag_fill` and the stats line read those values and never call `xTaskGetHandle` for a task that another task deletes (Codex High, Opus L2: the old self-delete could free the TCB between `xTaskGetHandle` and `uxTaskGetStackHighWaterMark`).
- Stacks in PSRAM (above), so a view that flaps no longer allocates 10.7 KB of internal stack per cycle; only the two TCBs (~0.7 KB) come and go (Opus L4). Rate-limiting re-creation was the other option; it would still churn internal RAM and delay the fallback.
- Old Ember servers keep the fallback: with no view the tasks are created at the first fallback and never stopped.

## Offline fallback (#26, 0.9.40)

Principle: Ember stays the only authority. Offline the knob shows what it last knew, labelled, and never advances shared state, decides or replays a press. Firmware only; server and protocol unchanged.

**Link state** (`components/link_state`, pure C, host-tested in `test_link.c`):
- Levels: `BOOT` (no answer yet; pages treat it as not offline), `ONLINE` (the last counted request succeeded), `DEGRADED` (1-2 counted failures in a row; pages show no change), `OFFLINE` (3 or more, `LINK_OFFLINE_AFTER_FAILS`, the old threshold). `BOOT` goes `ONLINE` on the first answer and `OFFLINE` after 3 failures, so a normal or post-OTA boot never shows the offline glyph or drops a press. `offline_since_ms` (monotonic) is the first failure of the streak that went offline; it reaches the transition log only.
- What counts (`link_counts`, table-tested): 200 and 304 with a body the knob understood are `OK`; a transport error (`-1`: connect, DNS, timeout, reset), 5xx, 3xx other than 304 and a 200 the knob cannot parse are failures; 401/403 (they lead to the existing "Not paired" state through checkins and the view fallback), 404, 429, other 4xx and an aborted long-poll change nothing. A loop pass without Wi-Fi is a failure, except in `BOOT` (association and DHCP take seconds; "Can't join" covers a knob that never joins).
- Wrong host (#39): until 0.9.43 a URL that answered only uncounted statuses (a captive portal's 302, a proxy's 301, an HTML 200 from another host) kept the knob in `BOOT` or `ONLINE` forever. Ember never redirects the knob's routes (the stored URL has no trailing slash, so no `ServeMux` clean-path 301) and its `/state` and `/v1/pomodoro/state` are always JSON, so three such answers in a row now go `OFFLINE`. A 200 whose body did not fit the 16 KiB buffer (`http_conn` cuts it at `cap - 1` and drains the rest; `.body_len` says how much came) is a skip, not a failure (`link_counts_body`, host-tested in `test_legacy.c` `test_oversized_state`): Ember sends `/state` with every session and no limit, so a valid but cut `/state` must not take a reachable Ember offline. The view path needs no such rule: a cut view is not a knob view and is not counted. The legacy Pomodoro body is a few fixed fields in a 512 B buffer. A view the knob cannot read (`answer is not a knob view`) still changes nothing: the view policy counts it as a server error and falls back to `/state` after three, and that answer decides; so a real Ember with a view this firmware cannot read never flashes offline. Still uncounted, by design: a host that answers every route with 404 (the same answer as an Ember without the view route, or with Pomodoro off), 401/403 or other 4xx stays `BOOT`/`ONLINE`: no fresh data, but no offline marks either.
- `gen` counts entries into `OFFLINE`. Level and `gen` are packed in one word (`link_state_word`) that the ember task stores in one atomic, so other tasks read a consistent pair; the zero word is `BOOT`, gen 0, so the atomic needs no initializer.
- Fed only by the ember task (`link_note` in `ember_client.c`). Pages read `ember_client_offline()` (the word is `OFFLINE` and an Ember URL is set). Bot, Pomodoro, weather and now playing all use it (now playing used to flip on the first HTTP error through `ember_client_link()`, which stays for diagnostics and "Not paired").

**Presses cannot be replayed** (Codex review of #38): a press is stamped at press time with Ember's link word and the Pomodoro source word (`pomo_press_t`). It is dropped at once when either is offline, and at send time `pomo_press_ok` sends it only if neither word was offline at the press, neither is offline now and neither `gen` moved, so a press from before an outage is never sent, even when the link is back by then. The 0.9.40 draft checked only "offline now": three presses queued while degraded, the third failure in flight, two drops while offline, then a successful GET, and the third press went out after the reconnect (`test_no_replay` shows that rule passing the press). When Ember's link enters `OFFLINE` the ember task drains the queue and the pending long-poll press at once, so `OFFLINE: NOT SENT` (4 s, `POMO_ACTION_OFFLINE`) shows when the press is dropped, not at the reconnect. When only the Pomodoro source enters `OFFLINE` (`src_note`, on the ember task in view mode or the pomo task in fallback) it drains the queue only: the pending long-poll press is still dropped by its stamp, but when it is next run (the next poll's `longpoll_idle` aborts at once and gates it), so its `OFFLINE: NOT SENT` can come up to one poll late.

**Pomodoro freshness**: the Pomodoro data has its own `link_state_t` in `pomo_client.c`. It is fed by every view attempt that is not aborted or a 429 (ok when the view was applied, the pomo block included or off) in view mode, and by every legacy `/v1/pomodoro/state` poll in fallback through `pomo_poll_counts` (host-tested): a 404 means off and counts as an answer, everything else follows `link_counts`, so 401/403, 429 and other 4xx change nothing (until 0.9.43 the legacy poll counted them as misses). Three misses make the page offline (estimate, labels, dropped presses) even while Ember's link is `ONLINE`; `pomo_offline` combines both words (host-tested in `test_pomo.c` `test_source_stale`).

**Per page**:
- Bot: offline sets the neutral `BOT_IDLE` mood (dim grey outline, no host label; it turns sleepy after `sleepy_after_s` like any idle) and shows a small grey link glyph (`LV_SYMBOL_WIFI`, Montserrat 24, `0x5A5A5A`, 140 px below the centre, clear of the "Can't join" label). A demo mood (long push) still wins for its hold time.
- Pomodoro: `pomo_estimate` + `pomo_est_label` (`components/pomo`, host-tested). Running: remaining is the last view's `ends_at` aligned to Ember's clock (`pomo_clock_sync_end`, the `X-Ember-Now` offset) minus now, clamped at 0: the same local clock as online, so the count does not jump at the disconnect. Phase line `OFFLINE` (note grey). At 0 the time shows `00:00` (dim) and the phase line `WAITING FOR EMBER`; the phase never advances on the knob, nothing is recorded (the knob has no chime). Paused: `PAUSED OFFLINE`. Parked or idle: `OFFLINE`; no timer: `--:--`. No state yet and not offline (boot): `CONNECTING` (was `OFFLINE`). The built-in Montserrat has no `·`, so the spec's `00:00 · waiting for Ember` is the time line plus the phase line.

## Capabilities and the view major (#27, Ember#341, 0.9.42)

## Display rotation (#45, Ember#386, 0.9.44)

The user can turn the knob's image upside down from the Ember app. Contract: Ember `docs/DEVICE-PROTOCOL.md` (Ember#388, merged as 01864b5); fixtures synced from 01864b5 (`config_default.json` and `checkin_reply_config.json` with `display.rotation: 0`, `config_custom.json` with 180, `checkin_req_caps.json` with `caps.rotations: [0,180]`).

- **Setting**: `display.rotation` in the knob config (next to `display.fast_link`), 0/90/180/270, default 0, always sent. `parse_rotation` in `knob_settings.c` (the one place that reads the key) keeps a whole number the firmware supports and turns anything else (90, 270, 45, 180.5, `"180"`, `null`, a top-level `rotation`) into 0. Stored in NVS with the rest of the settings blob, so it survives a reboot.
- **Caps**: `rotations: [0,180]` (`KR_SUPPORTED` in `components/rotation`). The serialiser leaves out values other than 0/90/180/270 and repeats, and leaves the key out when 0 is missing: Ember drops every caps field for an invalid list.
- **Why only 0 and 180**: the CO5300 MADCTL (36h) has only MY (bit 7) and MX (bit 6); bit 5 (MV, row/column exchange) is "don't care" in the datasheet (V0.00, 7.5.29). The `esp_lcd_co5300` driver sets MV in `swap_xy`, but the panel ignores it. LVGL software rotation needs a rotate buffer in internal DMA RAM that the knob does not have (2 draw buffers already take 113 KB), so 90 and 270 are not offered.
- **180 = hardware mirror** (`kr_panel`, `components/bsp_knob`): MX + MY plus `esp_lcd_panel_set_gap`. The glass shows frame (= GRAM) columns 6..471 and rows 0..465. The gap depends on the window MX/MY mirror over, which is **an assumption, unverified until checked on the knob**: `KR_MIRROR_W`/`KR_MIRROR_H` = 480. The rows are backed by the datasheet ("the gate resolution only can be set 480 lines", l. 226); the columns are not ("the source resolution can be adjusted", same line), and an ESPHome CO5300 user still saw the edge line after adding a rotation (`board.md` §5). With 480x480 the gap is (2, 14): frame column x lands on GRAM 477 - x and row y on 465 - y, the same visible frame columns 6..471 as at 0 degrees, mirrored about the glass centre. Both gaps are even, so 2 px windows (even start, odd end) stay 2 px pairs. At 0 degrees: gap (0, 0), no mirror, as before.
- **If the mirror window is narrower** (a persistent strip at an edge at 180): set `KR_MIRROR_W` (and `KR_MIRROR_H` if the strip is at the top or bottom) to the real even width. Below 478 the gap goes negative (472 gives -6); `kr_panel_in` then returns `min_x = -gap_x` and the rounder (`kr_round`, used by `area_rounder_cb`) starts every window at `min_x`, so no CASET goes below 0 and frame columns 0..5 (off the glass anyway) are not sent. Host-tested for every even window from 472x466 to 480x480.
- **Touch**: `tp_read` maps the CST820 point with `kr_touch` for the orientation last written successfully: at 180, x' = 477 - x, y' = 465 - y, clamped to the 472x466 frame. This mapping is glass geometry and does not depend on the mirror window.
- **Applied live, retried until it holds**: `set_rotation` only stores the wish (`kr_want`). `bsp_knob_15_md50et_rotation_frame()` runs at the top of every `frame_cb` (LVGL task, lock held, between frames, like the brightness queue in `panel_check.c`) and steps `kr_step`: when the panel's orientation differs from the wish it writes gap + MADCTL (`tx_param` first waits for colour transfers in flight), and on success invalidates the screen, so the next refresh (about 25 ms of DMA at 80 MHz) redraws everything. A failed write is rolled back to the old orientation and retried after 100 ms, doubling to at most 5 s, whether or not a new config arrives. If the rollback fails too, the orientation is unknown: it is logged as an error, touch keeps the last orientation written, and the wish is written again on the same backoff (no rollback to an unknown state). A new wish resets the backoff. At boot `main` sets the stored wish before `bsp_knob_15_md50et_init`, and `lcd_init` steps once before display on, so the first frame is already the right way up; a failure there is retried by the frames instead of stopping the boot.
- **Unchanged**: encoder direction, the button, the factory-reset gesture and snapshots (`snapshot.py` reads LVGL, so it is always upright).
- **Tests**: `test_rotation.c` (supported list, fallback, gaps and mirror, coverage and non-negative windows for every even mirror window 472..480 x 466..480, the rounder at 0, 180 and a negative gap, 2 px pairs, the image mirrored about the glass centre, touch on every 5th visible pixel, clamping; the state machine with an injected `orient`: no write for the same value, a failed apply retried with backoff and no new wish, the backoff cap, a failed rollback giving unknown + retry of the wish, recovery). Each new state machine and rounder test fails on a mutant restoring the old behaviour (retry only on a settings change; rollback result ignored; rounder clamped at 0). `test_device.c` `test_settings_rotation` (default, 180, every fallback, the round trip through a checkin's stored config); `test_caps.c` (`[0,180]` between `pages` and `view`, invalid values, repeats, no 0); `test_fixtures.c` (config rotation 0 and 180, the caps request byte for byte).
- **On the knob (not yet checked)**:
  1. Set 180 in the app: the image is upright with the knob turned over, within a checkin and without a reboot.
  2. Taps and swipes land where the finger is; swipe up/down still go the right way for the viewer.
  3. On the 0 → 180 switch, one frame may show a 14-row strip at the top edge (GRAM rows 466..479, never written) before the redraw lands: expected, not a bug.
  4. No persistent line, blank strip or shifted image at any edge at 180. A persistent strip means the 480-column/row mirror assumption is wrong; see "If the mirror window is narrower" above.
  5. Reboot: it comes back at 180 with no upside-down first frame.
  6. Set 0 again: the image is as before, with no edge line.

Image about 1,555 KB (`cinder.bin`); no new task, NVS key or LVGL object.
